# Conflux 决策记录（ADR）

版本：0.1；决策日期：2026-10-21。文档负责人：技术负责人；产品、平台、安全、发布与商业化负责人共同维护。

本文件记录进入实现前的决策及其约束，不把方案等同于已经实现或通过认证的能力。**v1 指 M3 商业化发布**；M0—M2 是验证和逐步开放范围，M4 是独立验证后的扩展。功能与验收见 [PRD](product-spec.md)，算法与接口契约见 [技术设计](technical-design.md)，排期、风险和商业假设见 [路线图](roadmap.md)。

事实采用三种表达：已有官方文档确认的能力附来源；产品自定义字段、阈值与行为注明为设计决策；外部 API、参数、路径或平台行为未确认时明确标注 `[待验证]`，不得以生产配置上线。来源核验截至 2026-10-21；API 存在不代表所有应用、远程工具和系统版本都支持该操作。

## ADR-001：使用约定技术栈，业务状态在 Rust core

| 项目 | 记录 |
| --- | --- |
| 背景 | 客户已确定 Tauri 2 + Rust core + React/TypeScript + Tailwind + shadcn/ui。跨平台难点集中于检测、窗口控制与恢复，设置 UI 应服务于相同业务契约。 |
| 选项 | A：约定技术栈；B：Electron；C：每个平台原生 UI；D：先改用单平台产品。 |
| 取舍 | A 避免重做已确定的产品技术前提，并允许 OS 适配集中于 Rust。代价是需要真实平台 FFI、WebView 兼容性和不同安装机制验证；不能从框架选择直接推出低于 120 MB 的内存结果。B、C 引入不必要的迁移与维护成本；D 不能满足三平台目标。 |
| 结论 | 采纳 A。一个普通用户应用实例拥有 UI 与 Rust core；所有业务状态、journal、规则执行、授权判定与原生操作归 Rust。React 只消费有类型的状态投影并发出允许的命令。前端不得任意执行 shell、任意读取文件或直接持有更新签名私钥。平台适配通过能力接口隔离；M4 helper 是另行安装的可选组件。Tauri 宿主加系统 WebView 可能产生子进程，因此“单进程 UI + core”是业务进程边界，不宣称整个进程树只有一个 OS 进程。 |
| 何时重审 | M0 无法满足关键平台窗口控制，或 M2 实测资源目标持续不达标且已完成 WebView 生命周期优化时，提交数据驱动的替代 ADR；不得以 UI 偏好改框架。 |

## ADR-002：v1 不创建虚拟显示器，M4 Windows 优先

| 项目 | 记录 |
| --- | --- |
| 背景 | 大多数 mirror 工具无法提供可依赖的“当前捕获屏”公共接口。虚拟显示器可成为专用目标，但仍需远程工具实际选择它；创建一块虚拟屏不等于远程端正在看它，也不等于被迁移的应用内容在物理屏上保持原样。 |
| 选项 | A：v1 集成三平台虚拟屏；B：v1 完成现有显示器上的迁移与救援，M4 分平台引入；C：只依赖第三方虚拟屏；D：永不做虚拟屏。 |
| 取舍 | A 将驱动签名、系统兼容、应用与显示驱动故障绑在首次发布中；macOS 私有 API 和 Linux 内核模块无法形成对称支持承诺。C 可用于验证与用户自选，但不能承担第三方驱动的维护和恢复责任。B 保留商业差异化，又让基础恢复先经过验证。 |
| 结论 | 采纳 B。v1 可以把用户已安装且 OS 枚举为可用的虚拟屏作为“指定显示器”，不安装、启停或保证该屏。M4 首先验证 Windows IddCx/IDD；完成驱动、Secure Boot、更新/卸载与断连恢复矩阵后才开放 Pro。macOS `CGVirtualDisplay` 的未公开接口及当前系统兼容性 `[待验证]`，只用于隔离实验，不承诺商用或 MAS 发布。Linux evdi 的支持内核、Secure Boot、DKMS 与授权/分发组合 `[待验证]`，先研究，不列入 M3/M4 的共同承诺。 |
| 何时重审 | M3 基础恢复达到发布门槛、付费访谈证明需求、驱动维护预算与签名主体落实后进入 M4；任一平台更新破坏恢复或签名资格不成立时停发该组件，不影响免费基础引擎。 |

## ADR-003：v1 无特权 helper，M4 Windows 按会话代理

| 项目 | 记录 |
| --- | --- |
| 背景 | 普通权限进程无法可靠控制所有高完整性窗口；在企业无管理员权限环境必须仍能运行基础功能。提权会增加安装摩擦、攻击面和更新复杂度。Windows 服务不能直接作为用户桌面的窗口控制器。 |
| 选项 | A：整个应用始终管理员运行；B：v1 安装常驻系统服务；C：v1 普通权限并明确跳过无权操作窗口，M4 增加可选 helper；D：借助未公开手段绕过隔离。 |
| 取舍 | A、B 让所有用户承担少数窗口需求的权限代价；D 不接受。C 降低支持面，代价是管理员窗口、其他用户会话、UAC 安全桌面无法纳入完整迁移成功率。 |
| 结论 | 采纳 C。v1 不装 helper，不要求以管理员启动；逐窗口报告权限失败并继续处理其他窗口。M4 Windows 可安装受签名验证的管理组件，并在目标交互会话中启动最小权限代理；Session 0 只管理生命周期和授权，不执行窗口枚举/移动。服务与代理的权限获取、令牌来源及启动细节 `[待验证]`，须经安全原型确认，不能假设普通用户令牌启动出的代理能操纵提权窗口。macOS 仅用户态 AX 与 `SMAppService` 登录项；任何 daemon 都不代替用户 TCC 授权。Linux X11 以当前用户访问当前显示会话，不以 root 扩大窗口能力；evdi 驱动安装是后续独立管理操作。 |
| 何时重审 | M2 权限失败成为可量化的高频需求且用户愿意安装附加组件时评估 M4；必须先完成威胁模型、按会话隔离、IPC 滥用、更新和卸载测试。默认安装不得因添加 helper 改成必须管理员。 |

Windows 明确禁止旧式交互服务设计；微软建议服务与用户会话进程通过受访问控制保护的 IPC 通信。见 [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)。macOS 13+ 的 `SMAppService` 覆盖 LoginItems、LaunchAgents 和 LaunchDaemons；该注册能力不等于窗口控制授权。见 [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)。

M4 IPC 只允许受限的窗口移动、状态读写及恢复动作；请求需绑定调用进程、用户、登录会话、启动实例与事务。Named Pipe 必须限制本机访问和 ACL；仅检查路径或签名不足以防止冒用，须从连接取得真实调用身份并验证签名、安装位置、会话及授权。具体协议、nonce 和错误码是项目自定义契约；禁止任意命令、任意路径写入、DLL 注入与调用方指定 token。代理不接受一个会话对另一个会话的窗口操作。

## ADR-004：X11 优先，Wayland 仅检测与通知

| 项目 | 记录 |
| --- | --- |
| 背景 | X11/EWMH 提供窗口列表与移动请求；Wayland 的隔离模型不提供通用的其他客户端窗口枚举和绝对定位能力。不能因为可检测远程会话，就承诺可以在 Wayland 上救援其他应用窗口。 |
| 选项 | A：宣称 Linux 完整支持；B：X11 支持，Wayland 降级；C：首发捆绑 KWin/GNOME 扩展；D：仅支持 XWayland 窗口并称支持 Wayland。 |
| 取舍 | A、D 会误导用户。C 需要适配不同 compositor 版本及扩展权限，扩大首发测试范围；B 能表达实际边界，代价是 Wayland 用户首发只有检测、说明与通知。 |
| 结论 | 采纳 B。v1 X11 在 EWMH/RandR 能力探测成功后开放迁移、布局与救援，WM 不支持或拒绝请求时读回并降级。Wayland 保留设置、可用会话信号、诊断和通知；自动迁移、自动恢复、off-screen rescue、通用全局热键均不承诺。XWayland 访问不得被误当成对所有 Wayland 应用的支持。后续 KWin scripting / GNOME Shell extension 作为显式安装、版本限定的适配器分别评审，具体扩展 API 和发布权限 `[待验证]`。 |
| 何时重审 | 出现足够覆盖目标桌面版本的公开协议，或一个 compositor 适配器通过完整窗口/恢复测试与维护成本评估时，单独把该组合由“不支持”升级为“部分支持”；不能整体升级“Wayland 支持”。 |

[EWMH](https://specifications.freedesktop.org/wm/latest-single/) 定义 `_NET_CLIENT_LIST`、`_NET_CLIENT_LIST_STACKING` 和 `_NET_MOVERESIZE_WINDOW`；请求是否被特定 WM 接受仍需读回验证。[Wayland 协议模型](https://wayland.freedesktop.org/docs/book/Protocol.html) 明确客户端不能访问其他客户端 surface，也不知道自身 surface 的全局位置。这是通用适配边界，不是缺少 root 权限。

## ADR-005：OS 内置信号与签名声明式规则混合

| 项目 | 记录 |
| --- | --- |
| 背景 | RDP 会话标志较稳定；mirror 工具进程驻留、后台监听和更新连接都可能被误判为远控中。厂商日志与协议会变动，不能把未验证进程名、端口、日志位置或正则写成默认自动规则。 |
| 选项 | A：全部检测编进客户端；B：全部放进可热更新规则；C：OS 适配器内置，工具差异用签名声明式规则；D：只依据进程名；E：只手动触发。 |
| 取舍 | A 修复慢；B 会使平台权限与复杂原生逻辑越过规则边界；D 误报不可接受；E 不满足自动化目标。C 可独立更新已验证工具知识，同时把原生能力和安全策略留在受审查代码中。 |
| 结论 | 采纳 C。OS 事件、会话语义和读取能力内置；签名 JSON 只声明组合、平台/工具版本、信号、权重、去抖及目标提示，不执行脚本或 shell。mirror 自动模式需至少两个独立证据家族、启发式分数 ≥ 0.90 且连续稳定 2 秒，其中至少一个证明入站交互连接；分数不是统计概率。关联进程与该进程的服务枚举不算两个独立证据。当前 Windows RDP session 的专用救援 guard 可使用受信 OS 权威来源，必须同时确认当前会话处于活动且未锁定状态，并存在本会话中满足越界谓词的合格窗口；只救援这些窗口，绝不能据此执行 mirror 集中。断开须为明确的最后一个活动连接结束，稳定延迟默认 15 秒、可配置 15–120 秒；恢复后自动触发冷却 30 秒。用户明确手动恢复可立即执行，手动动作可越过自动冷却。上述数值是设计起点，M0/M2 数据校准后修改需版本化。未验证规则仅 dry-run 或手动，不因分值高就允许自动。 |
| 何时重审 | authoritative session rescue 的来源、活动/锁定状态或空间谓词不能在平台门禁中可靠验证时，停用该例外并保留手动救援。其他来源若有明确、可靠的会话生命周期语义，须单独评审后才可新增例外；不得把例外扩展成 mirror 单信号自动化。出现误报或工具大版本变化立即降级该规则，回滚规则包而非降低全局门槛。新信号家族需要新增原生能力评审，不能靠 JSON 绕开。 |

补充约束：

- `WTSClientProtocolType` 的 0 为 console、2 为 RDP；它说明指定会话协议，不说明 TeamViewer 等是否在捕获桌面，更不说明捕获哪块屏。`SM_REMOTESESSION` 与同源 WTS 数据不得简单相加成为“独立双信号”。见 [WTS_INFO_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/ne-wtsapi32-wts_info_class)。
- `CGSessionCopyCurrentDictionary` 提供调用者的 Window Server 会话信息；从其存在推导“检测所有 macOS Screen Sharing 或第三方远控”是不成立的设计推断。相关可用键、连接语义与系统版本差异 `[待验证]`，M0 在真实连接/断开/共享屏幕样本下核对公开文档和实际返回值。见 [CGSessionCopyCurrentDictionary](https://developer.apple.com/documentation/coregraphics/cgsessioncopycurrentdictionary())。
- 进程白名单只限定允许的工具，仍须绑定已验证的入站连接事件并满足对应 guard。禁止“进程存在即自动触发”，不提供借白名单绕过检测门槛的选项；仅能确认进程存在时显示“无法验证连接，仅可手动”。
- 信号过期、观测断开、读取权限丢失或 unknown 不是明确断线：保留当前布局、停止自动断线推断并进入 Degraded。观测恢复后，若同一连接仍活动且没有恢复意图则返回 Active；只有已确认最后连接结束、显式恢复或需处理既有恢复事务时才进入 Restoring。锁屏、会话切换和休眠同样先冻结写入并保留 journal，不因无法读取信号而擅自恢复。
- 签名只证明来源和完整性，不证明检测准确。规则包应绑定客户端 schema 版本、有效期、发布序号、平台及工具版本；先干跑灰度，失败闭合到内置安全基线/最后已验证规则。kill switch 只禁用未来触发；已经存在的恢复事务继续完成。

## ADR-006：签名更新与恢复屏障，渠道独占更新权

| 项目 | 记录 |
| --- | --- |
| 背景 | 用户要求无感更新，但重启时窗口可能仍在临时布局。应用签名、Tauri 更新签名、规则签名是不同信任链；下载完成并不允许立即替换运行中的应用。 |
| 选项 | A：下载完立即静默重启；B：只提示手动下载；C：后台下载验证，安全点恢复后安装；D：所有渠道都用同一自更新器。 |
| 取舍 | A 破坏恢复契约；B 不能满足常规更新体验；D 与包管理器或商店所有权冲突。C 需要一个明确的更新协调器与可恢复 journal，但可使更新和窗口操作串行。 |
| 结论 | 采纳 C。直发渠道使用 Tauri updater 的签名校验，另加 OS 代码签名/公证。自动下载、校验与 staging 可后台进行；只有阻止新迁移、完成恢复和持久化、确认无未处理恢复项后，才允许安装/重启。Active 期间默认延后更新；若用户主动选择立即更新，则先恢复。权限不足、恢复未完成或系统限制时暂停安装并显示原因。灰度、签名发布清单、kill switch、保留上一可用包、健康启动确认和崩溃循环保护是 Conflux 自建发布契约，不宣称 Tauri updater 原生保证事务回滚。系统包管理器/企业管理/商店安装关闭应用自更新，由对应渠道负责二进制版本；规则更新服从企业策略。 |
| 何时重审 | 选择新的分发渠道或 installer、引入 helper/驱动、journal schema 不兼容，或更新事故表明安全屏障不足时必须重审。任何加速安全更新方案仍不得跳过恢复与签名校验。 |

[Tauri updater](https://v2.tauri.app/plugin/updater/) 提供签名校验与 Windows 安装模式配置。是否可完全静默取决于安装范围、权限和 installer；不能承诺没有 UAC、系统安全提示或包管理器交互。安装失败保持当前版本；安装后健康检查失败时，只有已验证数据兼容且旧包签名有效才自动回退。不能回退时进入禁用自动迁移的安全模式并提供已签名修复路径，保留 journal；不得反复升级/降级形成启动循环。

## ADR-007：年订阅、签名离线凭证及有界宽限

| 项目 | 记录 |
| --- | --- |
| 背景 | 平台和远程工具变化产生持续适配成本；用户可能在无互联网但局域网远控的环境使用。授权服务器故障不能让窗口失去恢复机会。 |
| 选项 | A：永久买断；B：买断 + 12 个月更新期；C：订阅且每次必须在线；D：年订阅 + 可验证的离线凭证。 |
| 取舍 | A 无法自然覆盖长期适配成本；B 有用户吸引力但增加版本授权和支持负担；C 破坏远程场景可靠性；D 支持持续维护，代价是维护授权服务、续订状态和离线边界。 |
| 结论 | 采纳 D。M3 建议价 **US$29/年**，同一自然人最多 **3 台激活主机**，**14 天免信用卡试用**；价格与转化目标是待市场验证的商业假设，不是已完成的支付配置。服务签发限定产品、设备、权益与期限的离线 entitlement；有效期最长 90 天，且不得超过 `paid_until + 14 天`。试用凭证不得超过 `trial_until`，没有额外宽限；这些字段是本项目自定义。正常联网时续签，网络失败不立即吊销仍有效凭证；到期停止新建/执行需 Pro 权益的配置，保留免费引擎、既有事务恢复、救援与安全更新。退款/撤销在在线同步后停止新的 Pro 操作，已经发生的窗口操作仍完整恢复。 |
| 何时重审 | M3 后以续费、退款、支持工时及用户调研评估买断方案；US$59 买断 + 12 个月功能更新只作为后续实验。企业隔离网络年度凭证与批量席位在 M4 单独设计合同与技术，不把消费者 90 天凭证直接改成年离线。 |

授权服务采用签名验证而非把可信逻辑放在前端；客户端不保存签发私钥。设备身份由可重置的安装标识和受保护的激活密钥构成，不依赖收集主板序列号等硬件指纹。系统时间回拨的可信时间锚点与密钥存储实现 `[待验证]`，须覆盖离线、系统重装和机器迁移测试；无法判断时限制新的 Pro 操作并保留恢复，不能把异常时钟变成窗口操作。离线撤销存在最长凭证有效期的传播延迟，这是明确接受的商业风险，不能宣称即时撤销。

## ADR-008：基础自动化免费，复杂工作流收费

| 项目 | 记录 |
| --- | --- |
| 背景 | 用户首先购买的是远控时可见且结束后可恢复的可靠行为。若把自动检测或恢复放进付费墙，用户无法充分验证产品且授权故障会破坏核心承诺。 |
| 选项 | A：所有自动化收费；B：免费基础闭环、Pro 高级工作流；C：全部免费仅企业收费；D：按远程工具品牌收费。 |
| 取舍 | A 降低试用质量；C 未验证企业销售能力；D 会让兼容性维护与定价耦合。B 使基础价值可持续体验，付费来自重复工作流和复杂配置，代价是免费用户也需要维护与支持。 |
| 结论 | 采纳 B。免费包含已验证规则自动检测、主屏/指定屏、手动触发、基础布局、迁移、恢复、救援、基础排除、热键、启动设置、诊断与更新。Pro 包含自定义/保存布局模板、高级规则编辑与组合、多远程并发仲裁。M4 验证后的虚拟屏为 Pro；企业策略、批量部署管理和组织支持进入企业版。免费在多来源重叠时采用保守合并与固定目标，不以付费墙阻止安全恢复；Pro 提供明确优先级和目标仲裁。未来能力必须按具体平台列出状态，不因付费升级就显示当前做不到的操作。 |
| 何时重审 | 付费转化与支持负担证明边界不合理时调整新销售方案；不得撤回已经承诺的安全恢复、救援和安全更新。任何已付费功能移除需明确迁移或退款策略。 |

权益变化只影响未来事务。试用/订阅结束不会在 Active 中途切换布局、删掉快照或强制关闭窗口；当前事务沿原计划恢复后，后续只采用免费配置。模板与规则保留可读、可导出，不把用户数据与付费状态一起删除。

## ADR-009：mirror 与 session 分开识别、共用 Window Engine

| 项目 | 记录 |
| --- | --- |
| 背景 | mirror 捕获当前交互桌面，其窗口仍可能分散在多屏；session 连接产生或重新连接一个拥有自身拓扑的会话，主要问题是应用保存了现已不可用的坐标。VNC、NoMachine 等品牌可能有多种模式，品牌名不能直接决定拓扑。 |
| 选项 | A：所有连接都搬到一块屏；B：完全独立实现两个引擎；C：分别定义意图与触发，共用窗口过滤、几何、journal 和验证。 |
| 取舍 | A 会扰乱 RDP 多显示器等本来可用的布局；B 重复恢复逻辑并增加分歧风险；C 需要显式拓扑分类，但使操作范围可以审计。 |
| 结论 | 采纳 C。mirror 执行“把允许的窗口收敛到确认的目标”；session 默认只救援当前会话中不可见的合格窗口，不把 console 窗口跨会话拉来，不重新排列已可见窗口。拓扑分类为 unknown 时只 dry-run/提示/手动。Windows 引擎绑定自身用户、Session ID 和交互桌面；macOS 绑定当前已授权登录会话；X11 绑定当前显示会话。快速用户切换、锁屏或会话失去可操作性时冻结新变更，保留恢复事务，待同一会话重新可用后重评估。 |
| 何时重审 | 工具新增真正独立会话模式，或合作方提供明确的 capture/session API 时，更新适配器与样本分类；不能根据一个产品营销名称把现有用户整体切换模式。 |

`WTSQuerySessionInformation` 可查询指定会话，跨用户查询有权限要求；`WTS_CURRENT_SESSION` 指调用者当前会话。它不授权跨会话窗口控制。见 [WTSQuerySessionInformationW](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsquerysessioninformationw)。

## ADR-010：目标屏由用户契约决定；强制单屏延后

| 项目 | 记录 |
| --- | --- |
| 背景 | 远程软件展示给客户端的 capture source 通常不可确认；默认猜测后直接移动窗口会制造“已经搬了仍看不见”的结果。禁用副屏能缩小选择空间，但会影响本地用户和第三方工具的显示列表缓存。 |
| 选项 | A：始终假设主屏是捕获屏；B：主屏默认 + 明确指定 + 热键循环 + 托盘提示；C：默认强制单屏；D：尝试每个平台未公开显示器控制接口。 |
| 取舍 | B 保留最低操作成本且让用户可以纠正；代价是不能承诺所有工具零配置命中。C 涉及黑屏、热插拔、HDR/刷新率/缩放变化、应用自重排和远程断联风险；D 不满足稳定产品边界。 |
| 结论 | 采纳 B。默认主屏，首次启用前显示当前目标和“需在远程工具中选择同一屏”的说明；用户可按稳定身份指定屏，热键循环与托盘示意同步反馈。规则提供的屏幕提示必须标“推测”，不覆盖用户明确选择。v1 不禁用输出。M4 仅 Windows 评估显式 opt-in 的实验强制单屏：预检、持久化拓扑、独立 watchdog、限时确认与回滚必须先通过故障注入。macOS 不承诺通用停用物理输出；X11 的 RandR/xrandr 改拓扑能力不自动升级为可靠恢复功能，首发同样不开。 |
| 何时重审 | Windows 上真机矩阵证实断连、应用崩溃、显示器热插拔与重启都能进入可恢复状态，且有用户需求时按工具/硬件 allowlist 开放；任何黑屏或不可恢复结果立即关闭该实验开关。其他平台须独立 ADR，不以“有 CGDisplay/xrandr”代替可行性证明。 |

Windows `SetDisplayConfig` 可设置当前会话的显示路径；`QueryDisplayConfig` 提供路径/模式信息，但 API 存在不保证任何远程会话都有访问权限或任何驱动都接受目标拓扑。见 [SetDisplayConfig](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setdisplayconfig)、[QueryDisplayConfig](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-querydisplayconfig)。macOS `CGDisplaySetDisplayMode` 是模式切换，`CGConfigureDisplayOrigin` 是显示器位置配置，不能把它们当作“禁用屏幕”的 API。见 [Quartz 显示模式文档](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/QuartzDisplayServicesConceptual/Articles/DisplayModes.html)、[CGConfigureDisplayOrigin](https://developer.apple.com/documentation/coregraphics/cgconfiguredisplayorigin(_:_:_:_:))。

独立 watchdog 只能在其仍能运行且 OS 允许恢复时执行补偿；断电期间无法执行任何软件恢复。产品承诺是在重新取得控制后优先救援并持续保留待恢复记录，不承诺对断电、驱动故障或第三方应用拒绝行为的绝对实时恢复。必须先恢复显示拓扑，再按当前实际拓扑恢复窗口；保存原始拓扑也不意味着可以原样重放已经拔掉的显示器。

## ADR-011：恢复以可见性和用户改动优先，持久化先于变更

| 项目 | 记录 |
| --- | --- |
| 背景 | 用户可能在远控中主动调整窗口；断开可能只是短暂重连；显示器可能拔掉；崩溃/断电会跳过退出回调。覆盖用户新布局与恢复到不存在的屏都违反产品目的。 |
| 选项 | A：断开立即无条件恢复精确坐标；B：从不自动恢复；C：事务快照 + 去抖 + 冲突感知恢复；D：只在内存保存快照。 |
| 取舍 | A 简单但破坏用户意图；B 不满足闭环；D 无法承担崩溃恢复。C 增加 journal 状态与冲突分类，但可以区分“没有恢复”和“安全地保留用户操作”。 |
| 结论 | 采纳 C。原始快照在第一次改变窗口前持久化并确认成功；失败则不操作。每次应用动作写入意图和实际读回结果；首次原始快照在同一事务生命周期中不可被断开重连、热键切目标或规则更新覆盖。默认 15 秒、可配置 15–120 秒的明确断开延迟内，重连合并进原事务；unknown 不启动该计时。默认尊重用户在会话中的手动移动/缩放；恢复时只对未冲突且身份可信的窗口应用原位置。有冲突但当前可见则保留；不可见则先夹到当前安全工作区，不因“尊重用户”而忽略救援。用户可在高级设置选择“强制恢复原布局”，只影响后续明确事务且仍受身份与可见性约束。 |
| 何时重审 | 真实样本证明应用自我纠正与用户移动难以区分，或默认冲突策略造成频繁困惑时，调整分类与提示，但不得把启发式结果冒充用户操作来源。任何 journal 数据丢失/错误恢复均阻止发布。 |

恢复语义的不可省略约束：

1. 原显示器缺失或身份有歧义时，选当前可见的安全工作区并夹取位置；不恢复到旧的全局坐标。显示器重连以后是否回原位属于新动作，不在后台持续和用户争夺位置。
2. 移动中的窗口被应用重新定位时有限重试并读回；预算耗尽后保留失败记录与可手动救援入口，禁止无限纠正。最小化窗口保持最小化，不为布局强行弹出；原生 fullscreen/独占受保护窗口默认跳过。
3. 正常退出、计划更新和正常卸载先进入 Restoring；尚有未完成项时不能标记“恢复完成”或删除 journal。明确选择保留当前可见布局须成为用户确认的终结记录；操作被拒/权限撤销时报告阻塞，不静默销毁证据。
4. panic、强杀、断电、系统强制注销不能保证执行退出处理；下次可运行且权限恢复后从 journal 接续。系统返回窗口、屏幕或权限失败时，“不永久不可见”落实为可检测、持久记录、下次优先救援和明确失败提示，而非无法兑现的无条件数学保证。
5. 规则回滚、许可证到期、工具切换、更新 kill switch 都不得取消当前恢复责任；只有确认恢复/安全保留/对象已销毁的窗口项可终结。

## ADR-012：窗口身份有生命周期，崩溃后不猜测认领

| 项目 | 记录 |
| --- | --- |
| 背景 | 窗口句柄、XID、PID 和显示器索引都可能重用；macOS AX 没有可直接承诺跨崩溃稳定的通用窗口 ID。错误地把旧快照应用到新的同名窗口，比一次不恢复更危险。 |
| 选项 | A：只保存句柄或标题；B：用复合身份并在不确定时拒绝自动认领；C：跨重启依靠标题/进程名模糊匹配；D：记录屏幕截图识别。 |
| 取舍 | A、C 会误伤新窗口；D 增加敏感内容采集且不能证明窗口同一性。B 在崩溃后可能需要用户确认，牺牲“无条件自动原位恢复”的表面体验，换取可解释的正确性。 |
| 结论 | 采纳 B。运行期身份包含 OS 会话、进程身份/创建时刻、平台窗口 token、内部 generation 与生命周期事件；generation 仅在可证明的连续生命周期中有效。Windows 的 HWND + PID + 进程创建时刻 + class 仍不能排除同进程 HWND 重用，不把该组合称为永久标识。AX 引用、窗口标题、窗口顺序和 XID 不能单独作为持久身份。崩溃后没有强证据证明仍是同一存活窗口时，只生成候选预览，用户确认后才应用旧布局；普通 off-screen rescue 可独立救援当前窗口，但不认领旧快照。 |
| 何时重审 | 某平台提供公开、可验证的稳定窗口身份，或应用合作适配器提供自己的持久窗口标识时，按该能力提高自动恢复范围；不能通过降低匹配阈值换取好看的恢复率。 |

显示器身份使用可用的设备路径、EDID 信息与系统提供的显示器身份组合，而非枚举序号。相同型号/缺失序列号、扩展坞变化、虚拟屏重建都可能使映射不唯一；平台获取路径、EDID 的具体链路与版本覆盖 `[待验证]`，由各平台负责人在 M0 用同型号双屏、换接口和热插拔验证。发生歧义时要求用户重新选目标或退回主屏救援，不把相同名称视为同一物理屏。

## ADR-013：最小权限、封闭命令面、无屏幕内容采集

| 项目 | 记录 |
| --- | --- |
| 背景 | 产品会读取窗口元数据、进程信息与可选日志，又允许更新规则改变触发时机；恶意规则、伪造 IPC、被入侵更新服务和本地文件篡改都可能引起不受欢迎的桌面操作。 |
| 选项 | A：万能脚本插件与全盘读取；B：受限信号 DSL、最小权限与多信任域；C：所有诊断上传服务器；D：仅依赖 HTTPS。 |
| 取舍 | A 适配快但相当于扩大执行入口；C 引入不必要隐私风险；D 无法阻挡服务端/分发供应链被替换。B 需要更明确的 schema、权限与密钥轮换，但使攻击范围可控。 |
| 结论 | 采纳 B。规则/二进制/授权采用隔离密钥与权限；规则只读已授权的受限数据源并只能请求业务允许的动作。没有远程脚本、远程 shell、注入或任意文件写入。应用默认不采集屏幕、剪贴板、输入内容或网络负载；不为基础窗口迁移申请 Screen Recording。窗口标题/路径只在用户主动建立相关规则时按需本地处理，默认日志不存原文；所有诊断导出先脱敏并让用户预览。匿名遥测默认关闭，授权状态与遥测同意分开。 |
| 何时重审 | 新增特权组件、第三方 SDK、云同步、屏幕内容能力或新的日志来源时，必须重新做权限/隐私评审；不能把新增采集塞进普通规则热更新。发生签名密钥泄露时按独立信任域撤销并保留恢复能力。 |

macOS AX 写属性可能被应用拒绝或超时，`AXUIElementIsAttributeSettable` 与 `AXUIElementSetMessagingTimeout` 可用于能力探测和控制等待；不因 TCC 授权存在就把所有窗口标为可迁移。见 [AXUIElement.h](https://developer.apple.com/documentation/applicationservices/axuielement_h)、[AXUIElementSetAttributeValue](https://developer.apple.com/documentation/applicationservices/1460434-axuielementsetattributevalue)。重装、签名身份变化后的 TCC 实际保留/失效行为 `[待验证]`，每次启动都重新检测权限而非假设旧授权有效。原生 fullscreen Space 与跨 Spaces 迁移不承诺；`NSWorkspace.activeSpaceDidChangeNotification` 只是变化通知，不是跨应用移屏接口，见 [Apple 文档](https://developer.apple.com/documentation/appkit/nsworkspace/activespacedidchangenotification)。

本地日志目录、规则探测路径及安装器静默参数在技术设计确认前不得靠名称猜测；生产实现必须来自锁定 SDK/插件或供应商文档与真机验证。文档中的内部协议和配置键是设计草案，不应被误读为已经存在的第三方 API。

## ADR-014：直发安装包优先，商店与企业渠道独立验证

| 项目 | 记录 |
| --- | --- |
| 背景 | 窗口管理、AX 授权、内核/特权组件和自更新对沙箱、包管理器及企业管理有不同要求。发布“有下载链接”和“渠道已审核可分发”不是同一件事。 |
| 选项 | A：首发同步所有商店与发行渠道；B：官网受签名安装包首发，已验证包管理渠道随后加入；C：只商店；D：所有平台用同一个安装器逻辑。 |
| 取舍 | A、D 放大发布支持面；C 会让产品能力受商店权限和更新规则约束。B 可以明确管理二进制所有权并逐步扩大覆盖，代价是自行维护签名、下载和信誉。 |
| 结论 | 采纳 B。Windows 代码签名安装包、macOS 签名并公证的 Universal 包、Linux AppImage/deb/rpm 按各平台契约发布；企业 MSI/PKG/deb 的策略、静默安装和卸载验证进入路线图。官网与 package metadata 可准备 winget/Homebrew Cask，但上架资格、实际审核和静默参数 `[待验证]`，不得作为已上线能力。Flathub、Microsoft Store、MAS 均单独验证沙箱、窗口控制、更新与支付约束。M3 不以这些商店审核作为前置，也不宣称已兼容；M4 驱动/helper 不能自动复用主程序渠道许可。 |
| 何时重审 | 用户获客或企业采购要求证明新渠道收益，且安全、权限与更新边界通过渠道原型后，再发布独立渠道方案。安装包变更必须重新测升级、降级、未登录卸载与 journal 保留。 |

Windows 10/11 x64/arm64、macOS 13+ Universal 和 Linux X11 是工程目标，不代表所有旧 OS 在销售时仍获得操作系统供应商支持。准确发行版、系统版本、架构和安全支持窗口由路线图和发布页按版本维护；发现供应商支持状态变化时明示支持边界，不靠宽泛的平台名称扩大承诺。

## ADR-015：能力矩阵决定发布范围，Fake 与真机验证互补

| 项目 | 记录 |
| --- | --- |
| 背景 | 无头逻辑测试不能证明真实 WM、TCC、UIPI、DPI、显示驱动或第三方应用会接受操作。macOS 私有虚拟屏实验也不能成为公开发行能力的证据。 |
| 选项 | A：只测核心状态机；B：全部人工回归；C：Fake 确定性测试 + 平台测试宿主 + 真机兼容矩阵；D：把不支持的窗口从结果中删除。 |
| 取舍 | A 不足以验收端到端；B 成本高且难覆盖时序故障；D 掩盖失败。C 将状态正确性与平台有效性分开，代价是维护硬件和远控组合，但可形成可复现的发布门槛。 |
| 结论 | 采纳 C。Window Engine、检测聚合、布局、身份和 journal 用 Fake 实现验证；平台适配通过真实宿主和真机读回验证。Windows 覆盖 DPI、提权、快速切换与 RDP/console；macOS 覆盖 Accessibility、拒绝/超时、Retina 和 Spaces 设置；Linux 覆盖不同 WM、RandR/Xinerama 与 Wayland 降级。`CGVirtualDisplay` 仅可用作 `[待验证]` 的隔离实验测试工具，CI 不得依赖它才能通过；真实双屏/三屏是验收替代。失败、跳过、权限拒绝和身份不明分别统计，不能将“跳过”混成成功。 |
| 何时重审 | 新增 OS 主版本、远程工具大版本、驱动/helper 或显示器模式时扩展对应矩阵。无法达到既定成功率/误报/延迟/资源门槛时缩小支持范围或延后发布，不通过修改统计分母掩盖。 |

性能验收要区分“检测达到触发条件的时间”“窗口批次命令提交”“实际读回收敛”。p95 < 300 ms 是规定测试负载下的引擎目标，不包括 2 秒确认、15 秒断开去抖或无限等候拒绝操作的应用；具体负载与测量边界以技术设计为准。三平台的空闲 CPU < 1%、RSS < 120 MB 需按同一进程树与采样规则测量，未测不得填“达标”。

## 决策变更规则

每项重审都需提交触发证据、受影响平台/用户、恢复与安全影响、迁移/回退方案和新验收条款；保留旧 ADR 并标为被替代，不悄悄改写历史结论。产品文案、支持矩阵、技术设计和路线图须在同一次文档变更中同步。`[待验证]` 关闭需要记录 SDK/OS/工具版本、验证步骤、结果与负责人；只找到一个近似名称或第三方代码片段不足以解除标记。

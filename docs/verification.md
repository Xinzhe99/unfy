```

before: visible 626x473+137+130  outer 640x480+130+130
observed: 626x473+-1783+52  delta=[0,0,0,0]  PASS

```

第一次运行时 delta 为 28 px，原因是不见边框（inset）方向写反；修正后为 0 px。

### 端到端迁移与恢复（`e2e` 二进制）

```
source \\.\DISPLAY1   1920x1032 @ 0,0
target \\.\DISPLAY2   1920x1032 @ -1920,-78
captured 6 windows
migration: applied=7 rejected=5 skipped=7 (desktop-wide)
migration PASS: every window is inside the target work area
restore: complete=false pending=2 (ours=0 others=2)
restore PASS: every window returned to its original rectangle (tolerance 4 px)
journal PASS: unresolved transaction kept 12 preimages for later recovery
E2E PASS (6 windows, real desktop)
```

`applied`/`rejected`/`skipped` 覆盖整块桌面的合格窗口，因为引擎的正确行为就是整理全部合格窗口。断言只覆盖测试自己创建的 6 个窗口。

`pending=2` 是桌面上两个第三方窗口（Chrome / Electron 系）拒绝被移动。产品行为正确：它们的 preimage 保留在 journal 中，事务保持未完成，而不是假装成功。**这也说明真实使用中，"全部恢复"通常不是 100%** —— UI 会显示待处理数量与进程号，而不是一个笼统的成功。

### 性能（100 窗口）

`e2e --stress 100` 在真实桌面上创建 100 个自己的窗口后测量：

| 运行 | 迁移 | 恢复 |
|---|---|---|
| 1 | 187 ms | 125 ms |
| 2 | 200 ms | 94 ms |
| 3 | 181 ms | 95 ms |

目标屏 1920×1032，容量 53 个窗口，其余 47 个按设计留在原位而不是压成不可用的小格。

**发现并修复的性能缺陷**：初版 40 窗口迁移耗时 **728 ms**，远超 300 ms 预算。定位到三处：

1. 每个窗口 3 次 `sync_all()`（preimage / intent / result）。改为按阶段批量：所有 preimage 一次 fsync 后才开始移动窗口，intent 每 16 个一批，result 在首轮结束后一次。
2. 重试在提交循环内同步 sleep，一个慢应用阻塞整批。改为两趟：首轮全部异步提交 + 读回，第二趟只重试偏离的窗口。
3. 每窗口重试 3 次且每次都 sleep。改为 2 次，且第一次重试不等待——观测中第三次尝试从未成功过。

改后 40 窗口 150 ms、100 窗口约 190 ms。

### 重复整理拦截

已经在 Active 状态下再次点击"整理到目标屏"：

```
窗口仍处于整理状态。请先点「恢复本次布局」，再重新整理到新的目标屏。
```

**发现并修复的缺陷**：修复前第二次整理会新建事务并用**当前**（已被移动的）位置作为 preimage，导致之后恢复把窗口送回错误的位置——引擎的单写者与"原始位置"不变量被破坏。现在 `migrate` 在事务未关闭时返回 `TransactionAlreadyOpen`，并有回归测试 `second_migration_keeps_the_original_preimage` 覆盖"恢复后再整理"的正确路径。

**发现并修复的缺陷（死锁）**：修复前勾选"登录时启动"会让命令线程永久阻塞——`save_settings` 持有设置锁的同时调用了会再次读取设置的 `apply_autostart`，而 `std::sync::Mutex` 不可重入。症状是设置文件已写入、注册表没写、UI 卡住。修复方式是把辅助函数改成接收目标值而不是自己取锁，并用 `drop(settings)` 明确表态；另加了一个回归测试固定这个约束。

### 退出屏障

托盘"退出"在还有未恢复窗口时会先尝试恢复，失败则取消退出并提示。该分支无法用 UI 自动化点托盘图标，所以在引擎层用 3 个用例固定：

- 刚启动的引擎不阻塞退出；
- 整理后 `has_pending_work()` 为真，恢复成功后解除；
- 接管的崩溃事务同样阻塞退出，恢复并清理 journal 后解除。

前端也补上了 `conflux://exit-blocked` 与 `conflux://update` 的监听——此前 Rust 会发这两个事件，但界面没有任何反应，用户点退出"没反应"且看不到原因。为验证而临时加的命令与辅助函数在验证后已删除，没有留在产品 API 里。

### 单实例

连续启动两次 `conflux.exe`：

```

### 布局列数（预览暴露的缺陷）

预览把 5 个窗口画成 5 条竖条。根本原因是网格评分里"空槽数量"权重高于"单元格长宽比"，于是 5×1（零空槽）胜出。

修正后按优先级：最小尺寸违反 → 浪费整行/整列 → 长宽比 → 空槽。9 个窗口曾落到 4 列（浪费一整列），一并修正为 3 列。新增 4 个用例固定 4/5/6/9 窗口的列数。

### 自动更新的检查链路

用一个 minisign 测试密钥和本地清单服务真实走了一遍检查流程（`tauri.conf.json` 临时指向
`http://127.0.0.1:8787/manifest.json`，验证后已还原为空配置）：

```
WARN the update download URL http://127.0.0.1:8787/artifact.bin does not use the `https` protocol
INFO update check finished outcome="failed"
界面显示：install failed: invalid updater binary format
```

**能证明的**：端点被读取、清单被解析、签名被校验、下载被执行、失败原因一路传到了界面。
最后一步失败是因为测试产物不是合法的 updater 包（用的是图标文件签的名），不是流程缺陷。

**发现并修复的缺陷**：在此之前 `check_update` 只返回字符串 `"failed"`，具体原因只写进日志。
用户点「检查更新」只会看到"检查更新失败，请稍后重试"，无法判断是网络、签名还是更新包格式。
现在 `UpdateOutcome::detail()` 把原因带回界面，设置页与提示条都会显示。

**不能证明的**：真实发布服务器可达、HTTPS 证书、以及一次真实升级后进程重启并保留用户状态。
这些需要真实发布环境，见 [release.md](release.md) 的首次发布清单。

### 前端渲染与设计约束

```
bun test
 32 pass, 0 fail, 65 expect() calls   (4 files)
```

四组测试，都是为了让"看起来正常"的东西不再靠肉眼把关：

| 文件 | 固定的事实 |
|---|---|
| `pages/render.test.tsx` | 每个页面在代表性数据下都能渲染（概览 4 种状态、显示器、排除、设置 2 种更新配置、引导 4 步、录制器、预览），空树或抛错即失败 |
| `lib/design.test.ts` | 除 token 文件外不得出现硬编码颜色；TSX 里引用的每个 `var(--color-*)` 都必须已定义；强调色在两个主题下 chroma < 0.02；语义色每主题只声明一次；页面必须用共享 `Card` |
| `lib/design.test.ts`（对比度） | 8 组文字/背景的 WCAG 比值均 ≥ 4.5，且 muted 明显浅于正文 |
| `lib/a11y.test.ts` | 纯图标按钮必须有可访问名称；`Switch` 的 `label` 是必填；导航是有名地标且带 `aria-current`；焦点有可见替代；尊重 `prefers-reduced-motion`；正文不得用裸白/黑 |

**测试立即抓到的真实问题**：`--color-muted` 在白底上只有 **3.96:1**，而它承载全站 11px 提示文字——
低于 WCAG AA 对正文的 4.5:1。调整到 `oklch(0.535 …)` 后为 5.18:1（画布上 4.79:1），同时仍明显
浅于正文。这个问题在任何截图里都"看着没问题"。

**关于截图**：验证到这一步时机器的会话已锁屏，`PrintWindow` 与全屏截图都会返回锁屏画面，
不能作为界面证据。因此改用无头浏览器渲染 `dist/`，并用一份 IPC stub 提供代表性数据
（见 `.verify/update/ui-stub.js`，不随产品发布）。逐页核对结果：

| 检查 | 结果 |
|---|---|
| 概览（浅色 / 深色） | 状态、目标屏、远程检测证据、活动历史、工具分区层级清晰；深色下选中导航有可见底色 |
| 显示器（浅色 / 深色） | 真实截图占位、编号角标、选中描边；深色下未选中角标改为固定深色底 |

| 设置（浅色 / 深色） | 检测灵敏度、自动整理/恢复、快捷键录制按钮、更新状态"未配置更新源" |

### 显示器卡片按真实位置排布

截图里的两块屏是 `DISPLAY2` 在 x=-1920（左）、`DISPLAY1` 在主位（右）。原来的 2×3 网格
把两块屏并排画出来，**编号却是平台枚举顺序**：左边卡片写着"2"，右边写着"1"。

这不是排版问题：屏幕上闪烁的编号由 `identify_displays` 绘制，用的也是枚举顺序。用户在远程
画面里读到"1"，回头点左边那张卡片，实际选中的是另一块屏。

修复分两处，共用一条规则 `DisplaySnapshot::ordered_by_position`（从左到右、从上到下）：

1. 卡片按真实坐标绝对定位，垂直堆叠的显示器会画成上下而不是并排；
2. 屏幕上的编号与卡片使用同一个函数排序。

**布局本身踩了四次坑**，每次都留下截图证据：

| 尝试 | 结果 |
|---|---|
| `aspectRatio` 派生容器高度 | 两块 1920×1080 并排 → 容器 40px 高，卡片成细条 |
| 按"最高卡片占比"反推高度并设上下限 | 上限截断后卡片仍只有 50px，下方留半屏空白 |
| `aspectRatio` + 百分比单元格 | 容器被压扁，卡片成薄片（截图可见） |
| **固定行高 × 行数 + 绝对定位** | 正确：卡片可读、位置保真、无空白 |

最终方案不依赖宽高比：每行 9rem，容器高度 = 行数 × 9rem，单元格用百分比定位到容器内。
宽度仍按真实像素比例分配，所以 1920×1080 与 2560×1440 的卡片宽度不同——这也顺带证明了
布局读取的是真实几何而不是均分。

三个 domain 测试固定排序：x 为负的屏排第一、堆叠时上屏排第一、单屏稳定。

### 「保留当前布局」——退出屏障的第三条路

退出时的提示一直写着"请先恢复布局，或选择保留当前布局"，但**这个选项在任何界面里都不存在**。
`Engine::keep_current_layout` 有实现也有单元测试，却没有任何命令或按钮调用它。结果是：
恢复不成功的用户无法退出——托盘拒绝退出，界面也没有别的出路。

```

语义是明确的：关闭 journal 并丢弃 preimage，从这一刻起当前布局就是新的基准，下次整理会把它

### 状态机里的死状态

`EngineState::Error` 从定义起就**从未被赋值**，只在 `migrate` 里检查过。而它描述的情况是真实的：
journal 无法写入时，durability 保证已经不成立。

真正的后果不是"这个状态没用"，而是**应用会卡死**：`migrate` 先把状态设为 `Migrating`，
随后 journal 写入失败用 `?` 提前返回——状态就永远停在 `Migrating`。之后每一次调用
（整理、恢复、重新整理）都被 `InvalidTransition` 拒绝，界面显示"正在整理"，直到重启进程。

修复后 journal 写入或 `durable()` 失败都会进入 `Error`，并且：
- `rescue_offscreen` 与 `restore` 在 Error 下仍然可用（用户必须有出路）；
- 新的整理被拒绝，而不是在一个可能不持久的 journal 上继续。

测试用一个"父路径是文件"的目录制造真实写入失败，断言状态变为 `Error`、救援仍可用、
再次整理被拒绝。把 Error 赋值去掉后该测试失败，报 `left: Migrating, right: Error`。

### 设置保存了但没生效

`save_settings` 在事务进行中调用 `engine.update_config` 会被拒绝（当前计划是用旧设置算的，
中途替换会让 journal 与预览不符）。这本身是对的，但调用方只写了一行 `warn!`：磁盘上已是新值，
运行中的引擎仍是旧值，用户改完布局发现下次整理没变化。

现在这条路径会写入 `last_error`，概览页显示"设置已保存，但当前整理还在进行中，新的布局会在
下次整理时生效"。

### 恢复延迟：实测

设置 4 秒延迟后点「恢复本次布局」：

```
19:19:02.750  INFO restore delayed; a new gather will cancel it seconds=4
19:19:06.751  INFO restore delay elapsed; restoring now
19:19:06.754  INFO restore finished restored=1 pending=0 state=Idle
```

精确 4.0 秒，界面同时显示递减倒计时（观察到"2 秒后恢复布局"）。

**发现并修正的设计错误**：自动恢复原先**跳过**延迟，理由是"检测器已经观察了几轮"。这恰好废掉了
延迟存在的理由——延迟就是为"断开后很快重连"设计的，而 RDP 与手动标记是**立即**转换的，重连
必然导致"恢复 + 再整理"两次搬移。现在自动恢复也遵守延迟，且挂起的恢复会被新的整理取消
（`Schedule` 的世代计数），取消时静默返回而不是记成"恢复了 0 个窗口"。

三个测试驱动真实的 `Schedule` 与 `wait_cancellable`，验证取消能打断等待。

### 三个整理入口都取消挂起的恢复（代码审查 + 单元测试）

延迟机制的前提是"重连会杀掉计时器"。检查三个入口时发现：

| 入口 | 是否取消挂起的恢复 |
|---|---|
| 界面「整理到目标屏」 | 是（`commands.rs`） |
| 全局快捷键 | **否** → 已补 |
| 检测器自动整理 | **否**（我上一轮声称已实现，实际没有）→ 已补 |

同时移除了 `monitor::restore` 里等待结束后对自己 token 的 `cancel()`：它取消的是自己，
既无意义又会让下一次 claim 从不同世代开始。

7 个单元测试驱动真实的 `Schedule` 与 `wait_cancellable`：重连取消恢复、未取消时正常执行、
取消后不阻塞下一次恢复。

**实机验证的局限**：尝试用合成 `Ctrl+Alt+G` 验证快捷键路径，但按键没有送达 WebView（本环境
的已知限制），日志显示恢复按 10 秒延迟正常执行——这只证明"未收到取消时会恢复"，没有证明
"收到取消时会中止"。快捷键与检测器路径的取消依赖上述代码位置与单元测试。

sample: {'affected': 1, 'at': 1792610603, 'kind': 'restore', 'trigger': 'window', 'unsettled': 0}
```

**隐私核对**（对导出文件做字符串扫描）：

```
clean: 'title'   clean: '.exe'   clean: 'C:\'   clean: 'DISPLAY#'   clean: '\\?\'
```

无窗口标题、无应用名、无原始设备路径、无用户目录。文件 5499 字节。

一个测试固定入口字段的形状：序列化结果不得出现 `title` / `path` / `url` / `user` / `app_name`。

### 只读操作失败后不能把引擎留在忙态

`preview` 先把状态设为 `Planning`，再用 `?` 返回 `build_preview` 的错误。失败时状态就永久停在
`Planning`——此后整理、恢复、重新整理、甚至再预览一次，全部被 `InvalidTransition` 拒绝，
只能重启进程。

这与上一轮修的 `EngineState::Error` 是同一种缺陷，只是发生在只读路径上：预览什么都没移动，
失败后回到 `Idle` 才是诚实的终态。

同一轮还修了 `migrate` 中途 `enumerate` 失败：那会让状态停在 `Migrating`，同样不可操作。
现在改用 `Degraded`（journal 已有 preimage，恢复可用）。

测试用"不存在的显示器"触发失败，断言状态回到 `Idle` 且后续整理仍然成功。把修复去掉后
测试报 `left: Planning, right: Idle`。

### 取消暂停不能把"部分完成"说成"全部完成"

`resume` 原本只在有事务时直接把状态设为 `Active`。`Degraded` 的三种来源都被它覆盖：

- 接管了上次崩溃留下的事务；
- 迁移中途平台失败；
- 计划里一个窗口都没放进去。

`Degraded` 的含义是"还有窗口没处理"。概览页据此在"恢复"与"保留当前布局"之间选择，覆盖它等于
告诉用户布局已完成，而实际还有残留。

现在只在原本不是 `Degraded` 时才恢复为 `Active`。测试用真实路径构造：整理 → 丢弃引擎 →
对新引擎 `recover_latest` 接管未完成事务 → 断言状态为 `Degraded` → 暂停 → 取消暂停 →
仍为 `Degraded`。去掉修复后测试报 `left: Active, right: Degraded`。

### 窗口隐藏时停止轮询

关闭窗口只是隐藏它，进程继续在托盘运行。原来每 4 秒无条件刷新一次，每次 **8 个命令**：
`get_status`、`list_displays`、`get_settings`、`pending_work`（扫描 journal 目录）、
`hotkey_status`、`update_status`、`activity_log`（读整个历史文件）、`health_check`（写盘探测）。

`document.visibilityState` 在 Tauri 隐藏窗口时**不会变化**——先按 Web 标准加了
`visibilitychange` 监听，实测隐藏后 CPU 仍以可见速率增长。改用后端在隐藏时发
`conflux://window-hidden` 事件，前端停表；窗口重新获得焦点时恢复。

计数验证（临时探针，验证后移除）：

```
可见 12 秒：轮询 5 次
隐藏 12 秒：轮询 0 次
```

**CPU 测量不可靠**：可见 0.094s / 隐藏 0.078s（10 秒），差异小于采样噪声，因为 WebView
自身的空闲开销占主导。轮询次数的直接计数才是有效证据。

### 磁盘写入从"每 4 秒"降到"每 10 分钟"

`health_check` 里的存储检查会创建并删除一个探针文件。它被前端每 4 秒轮询一次——也就是说
**窗口开着的时候，程序一直在写盘**，为了一个几乎从不变化的事实。

改为缓存 10 分钟。探测本身的实现（`ShellExecuteW` 之前的 `create → write → remove`）不变，
只是不再每次轮询都跑。

### 打开配置目录

诊断导出后只显示完整路径文本，用户需要自己去找。现在概览「工具」里有「打开配置目录」，
经 `ShellExecuteW` 调用系统文件管理器。

后端只允许打开配置根目录下的路径：请求可以省略参数（表示配置目录本身），显式传入的路径会
与配置根做前缀校验。否则这个便捷入口就成了任意目录读取原语。

探针实测：`dir exists: true` → `open_directory -> true`。

### 快捷键的发现性

产品默认不设快捷键（避免占用用户已有的组合键），但这意味着**新用户永远不知道有一键整理**——
而"一键"正是核心卖点。实测这台机器上两个快捷键一直为空。

设置页在两者都为空时提供「使用建议组合」，一次写入 `CmdOrCtrl+Alt+G` 与 `CmdOrCtrl+Alt+R`。
实测：

```
hotkey_gather: CmdOrCtrl+Alt+G
hotkey_restore: CmdOrCtrl+Alt+R
日志：无注册冲突
界面：Ctrl + Alt + G / Ctrl + Alt + R，无"未生效"提示
```

概览页另有提示：既没设快捷键、检测也关闭时，说明"现在只能从本窗口或托盘触发"。

**为什么不是默认值**：默认占用系统组合键会在用户已有快捷键的应用里静默抢键，这是更糟的体验。
建议按钮把选择权留给用户，同时让功能可被发现。

### 恢复延迟的默认值与作用范围

规格写的是"默认 15 秒、可配置 15–120 秒的明确断开延迟内，重连合并进原事务"。实现里默认是
**0 秒**，上限 60 秒——也就是说这个保护默认从不生效。改为默认 15 秒、上限 120 秒。

更重要的是**作用范围**：延迟只应作用于"检测到远程会话结束后自动恢复"这一条路径。

| 入口 | 是否等待 | 理由 |
|---|---|---|
| 概览「恢复本次布局」 | 否 | 用户点了就要它执行，等 15 秒像按钮坏了 |
| 托盘「恢复本次布局」 | 否 | 同上 |
| 快捷键恢复 | 否 | 同上 |
| 退出时恢复 | 否 | 同上 |
| 检测到会话结束后自动恢复 | **是** | 期间的重新整理会取消它，这才是延迟的用途 |

修正前除退出路径外都会等待。实测（延迟设为 15 秒）：手动点击恢复后日志里没有
`restore delayed`，直接出现 `restore finished restored=2`。

### 循环切换目标屏（规格 P0-04-B）

按产品规格逐条核对时发现这一项**完全未实现**：远程端只有一块屏时，用户无法快速切换显示哪一块。

托盘与显示器页都加了「切换到下一块屏」。它委托给 `Engine::retarget`，因此天然满足规格的
不变量——**不覆盖原基线**。实测连续切换两次：

```
目标: DISPLAY1(编号 2) → DISPLAY2(编号 1) → DISPLAY1(编号 2)
20:04:11.038  restore finished transaction=5e625c62 restored=2 pending=0 Idle
20:04:11.123  migration finished transaction=8d6c1b69 applied=2 state=Active

说明原基线没有被中间布局覆盖。

单显示器时托盘项禁用而不是隐藏，避免设备变化时菜单项忽隐忽现。

### 休眠唤醒后不复用旧观察（规格 P0-10-B）

监控线程用"两次轮询的实际间隔远超 2 秒"判断机器休眠过，不依赖各平台的电源事件回调。

**第一版实现是错的，而且比不做更糟**：它重建了整个 `Tracker`。新 tracker 没有活动证据，下一次
轮询就会报告 `Deactivated`，于是**用户还在远程、机器只是睡了一觉，应用却把所有窗口搬回去了**。

正确做法是只丢弃**观察**（连击计数、上次证据摘要），保留判定：

| 重置什么 | 理由 |
|---|---|
| 连击计数（streak） | 计数跨越休眠没有意义 |
| 上次证据摘要 | 否则真实变化不会写日志 |
| **不重置**：活动判定 | 重建会让下一次轮询伪造"会话结束" |
| **不重置**：手动标记 | 那是用户的声明，不是观察 |

三个测试固定这个语义，其中一个专门断言"重建 tracker 会伪造会话结束"——把错误实现写成
测试，未来有人改回去会立刻失败。

实机运行 10 秒，日志中没有误报的 `long gap between polls`，说明正常路径不触发休眠处理。

**未验证**：真实休眠/唤醒场景（无法在验证环境安全挂起系统）。

### 关闭自动整理时先恢复（规格 P0-11-B）

规格要求"关闭自动整理默认先恢复"。此前关闭只是一个开关：窗口仍停在整理后的位置，而自动整理
已经不再工作——功能关掉了，效果还在，且下一次整理没有基线可回。

现在关闭时先执行恢复。实测：

```
20:17:29  migration finished  applied=2  state=Active
20:17:56  restore finished    restored=2 pending=0  state=Idle
20:17:56  automation disabled; layout restored
journal: 1 → 0    auto_gather: False
```

设置页的说明也随之改变：开关打开时显示"关闭时会先把窗口恢复原位，再停止自动整理"，
用户在动手之前就知道会发生什么。

锁顺序：`save_settings` 先读引擎状态再取设置锁，与其余路径的 engine→settings 顺序一致，
避免并发时死锁。

### 中英双语界面（规格 P0-11-A）

界面文案全部经过 `t()`，语言在设置页切换（跟随系统 / 中文 / English）。

**设计取舍**：用中文原文作键（`t("就绪")`），而不是 `t("overview.status.ready")`。好处是缺失英文时
回退到中文而不是渲染出键名——后者在运行时看起来像崩溃；代价是改中文会孤立对应译文。

**实现中修掉的三个真实缺陷**：

1. **`navigator.language` 可能是 `undefined`**。原代码直接 `.toLowerCase()`，在某些 WebView 与
   Bun 测试环境会抛异常——而那发生在模块加载期，**整个界面会白屏**。测试抓到了这个。
2. **语言应用时机错了**。最初放在 `useEffect` 里，`t()` 在首次渲染时读的是旧值，之后也没有
   重渲染——切到 English 后界面仍是全中文。改为渲染期同步 apply（值只由 `settings.language`
   派生，因此可重入安全）。
3. **活动历史的 note 由 Rust 写中文**（`先恢复了 2 个窗口`），在英文界面里原样出现。改为写
   结构化键值 `restored_first=2`，前端按当前语言渲染句子。

**覆盖测试**：扫描所有 `.tsx` 的中文字面量与中文 JSX 文本，要求每个都能在目录里找到英文条目。
这条测试当场发现了 5 处折行导致键不匹配的文案。

实机验证：英文界面导航、状态、按钮、活动历史全部为英文；切回中文完全正常，无回归。

### 英文界面的视觉复核

逐页在英文下截图核对，发现两类问题：

**漏翻译的运行时文案**。批量替换只覆盖了 JSX 字面量，以下位置全部漏掉：

- 分段控件的选项数组（`{ value: "dark", label: "深色" }`）
- 三元分支（`? "既然全部屏幕都看得到…" : "默认。远端只有一块屏…"`）
- 函数返回值（`humanError` 的每条文案、`detectHint` 的 default 分支）
- 模板字符串片段（`；${apps} 没有接受位置调整`）

**覆盖测试随之加强**：现在扫描所有含中文的字符串字面量，不只是 JSX 文本。加强后立刻多找出
十余处，包括 `已检测到`、`正在恢复…`、`没有可用的显示器` 等。

**布局**：卡片行高从 9rem 提到 11rem。英文的 `Display 2 (primary)` 会折成两行，9rem 下
截图区被压成一条。

### 后端文案的语言（本轮）

英文界面复核后发现：**后端在 Rust 里拼好中文句子发给界面**，这些句子在英文界面里原样显示。受影响的
有健康检查项、活动记录的备注、错误提示、远程会话证据、托盘菜单。

**机制**：新增 `Message { key, params }`。后端只决定"说哪一句"并给参数值，前端用目录渲染句子。键就是
中文原句（与前端目录同一约定）。参数值也过一遍 `t()`：权限名这类参数本身就是目录键（`辅助功能` →
`Accessibility`），而数量、路径、系统错误不是键，`t()` 原样返回。

**托盘**在 Rust 里渲染，读不到前端目录，因此有自带的语言表（`ui_text.rs`），含菜单项、提示语与证据句。
语言由前端解析后通过 `set_ui_locale` 告知后端——两条独立的解析规则会给出不一致的结果（中文托盘配英文窗口）。

**顺带修掉的真 bug**：
- `monitor.rs` 返回中文 `没有可用的显示器`，而前端 `errorMessage` 找的是哨兵 `no_displays`，所以提示
  漏出中文原文。
- `last_remote` 只写不读（死状态），删除。
- `stateHints` 导出但无人使用，删除；`stateLabels` 与 `App.tsx` 的 `stateLabel` 是重复表，合并为一。
- `api.ts` 的 4 张标签表从未翻译：跳过原因、状态标签、状态提示、错误映射。新增测试逐条覆盖。

### 测试的两个盲点（已修）

1. **`known.has(literal)` 让目录键免检**。引导页标题写作 `title: "这个工具做什么"`——既是目录键又是
   未包装的字面量，于是通过。判据从"是否在目录里"改为"渲染出来是否还有中文"。
2. **文本扫描看不到渲染结果**。改为用英文渲染每个页面并断言无中文（含全角标点）。这条当场找出
   十余处，包括引导页、跳过原因、权限提示。

### 首屏不再假称「就绪」

窗口在 **0.37 秒**出现，内容在 **1.1 秒**（冷启动约 3 秒）就绪。之间这段时间里，侧栏芯片显示
「就绪」——应用在还没有读到任何状态时就断言了状态。现在 `status` 与 `settings` 到达前显示
「正在载入…」，芯片用中性色。

验证方式：Tauri 的**同步命令跑在主线程**，直接 sleep 会阻塞窗口消息泵（第一次尝试就让整个应用无响应、
UIA 读不到内容）。改成 `async fn` 后 sleep 落在运行时线程，窗口保持可读，于是在延迟期间观察到了载入态：
侧栏与内容区同时显示「正在载入…」。之后已移除该延迟并确认正常启动。

### 漏译的两个新成因（本轮）

英文复核继续发现漏译，成因和前两类不同：

1. **包装了但没有英文条目**。上一轮按「源码里的中文」搜索来加包装，英文条目是另一次搜索加的，两边没对齐。
   约 20 个键处于「会走 `t()`、但目录里没有英文」的状态，运行时回退到中文。新增静态测试：源码里每个
   `t("…")` 的键必须在目录里——它当场列出全部 20 个。
2. **未被渲染到的状态**。英文渲染测试只渲染每个页面的一种状态。于是「布局已启用」时的按钮
   （`恢复本次布局`、`暂停`）、单显示器空状态、降级提示、证据句（`{name} 已连接`）全部漏掉——证据键
   甚至**完全没有中文以外的条目**，英文界面里一直是中文。现在覆盖：概览的 6 种状态、引导 5 步全部、
   权限提示与待恢复卡片（从 `App.tsx` 抽成 `components/prompts.tsx`，此前无法被任何测试渲染）。

**实机复核另外发现的两处**（测试未覆盖）：
- 闪条拼接出 `Gathered 5 windowsskipped 7.`——子句之间没有分隔符，中文同样是
  `已整理 5 个窗口跳过 7 个。`。修法是让每个子句自带分隔符。
- 待恢复卡片里的 `有 {n} 个窗口的快照仍待处理` 是裸 JSX 文本（紧邻表达式的文本，文本扫描与 JSX 扫描都够不到）。

**深色主题**：配色一致，但窗口标题栏由操作系统绘制，浅色系统下深色界面配浅色标题栏。改为在主题变化时

### 三条入口，一套实现（本轮）

整理与恢复各服务三个入口：窗口按钮、托盘菜单、全局快捷键。此前：

- **整理**有三份实现。托盘与快捷键各自解析目标、调用引擎、写活动记录，因此都不持久化「拒绝移动的应用」
  （概览里的排除入口消失）、不写 `last_error`、不发进度事件。
- **恢复**虽然共用 `restore_after_delay`，但该函数内部硬编码 `trigger: "window"`，而快捷键与托盘随后
  各自再追加一条记录——从这两个入口恢复会写**两条**历史，其中一条还谎称来自窗口。

现在四个入口全部调用 `migrate_with_trigger` / `restore_with_trigger`，由调用方说明来源。

验证方式：托盘菜单无法程序化打开、合成按键到不了 `RegisterHotKey`，因此用临时钩子直接调用快捷键回调。

**这个钩子还抓到一个自己制造的事故**：用索引切片重写 `emit_action` 时，把恢复的代码拼进了整理分支并
删掉了恢复分支——快捷键「整理」实际在恢复，「恢复」成了空操作。是钩子的日志
（进入分支却没有「完成」）暴露的。索引式重写不可靠，改用整段替换。

### 自动整理会冻结整个应用（严重，已修）

**现象**：远端会话被检测到时（含手动标记），若窗口是打开的，整个应用停止响应——不是慢，是永久卡死。

**定位过程**：用临时钩子直接调用监控的 `tick`（等价于界面上的「标记为远程会话」），并在关键步骤打点。
日志停在 `retarget done` 之后、`refresh` 之前，同时监视器线程也停止轮询——说明调用线程持有某把锁卡住了。

**两处叠加的原因**：

1. **自锁**：`monitor::gather` 在**仍持有 settings 守卫**时调用 `tray::refresh`，而 `refresh` →
   `build_menu` 会再次去取 **engine** 锁。`std::sync::Mutex` 不可重入，于是该线程卡在自己身上；
   更糟的是 settings 守卫一直不放，主线程下一次轮询 `get_status`（engine → settings）就永久等待——
   界面因此冻结。修法：settings 只用于读取目标显示器 id，读完立即释放；并在 `refresh` 上写明
   「调用方不得持有状态锁」。
2. **锁顺序反转**：`monitor::gather` 先取 settings 再取 engine，而包括 `get_status` 在内的其他路径
   都是 engine 先。新增源码级测试固定该顺序（`settings_are_never_held_while_the_engine_is_taken`），
   已验证：还原顺序会让测试失败并点名 `monitor.rs:gather`。

**验证**：端到端跑通自动化——标记远程会话 → `auto_gather · 5 个窗口`；结束标记 → 延迟 3 秒后
`auto_restore · 5 个窗口`；全程 `Responding=True`。临时代码与调试日志已移除。

### 显示器拓扑缓存永不刷新（严重，已修）

为了验证「拓扑变化救援」这条路径，我临时把主显示器分辨率改成 1280×720（用
`ChangeDisplaySettingsEx`，**不写注册表**，因此重启即可恢复）。结果发现：

- 应用仍把该屏报告为 **1920×1080**——`WinDisplays::snapshot()` 只在缓存为空时枚举，
  而 `invalidate()` **从未被任何代码调用**（平台层没有窗口，收不到 `WM_DISPLAYCHANGE`）。
- 于是 `session::watch_topology` 每 2 秒比对的是一份**永不变化的签名**：它永远不会触发。
  「拔掉显示器时把窗口救回可见区域」这个功能实际上从未生效过。布局也会按旧工作区计算，
  可能把窗口放到实际屏幕之外。

**修法**：给缓存加 1 秒 TTL（枚举只需几百微秒，监视器节拍是 2 秒；`invalidate()` 保留给
确知发生变化的调用方）。缓存规则提取为可注入时钟的函数，新增 4 个测试：新鲜条目复用、
过期条目重读、`invalidate` 强制重读、读取失败不污染缓存——已验证旧逻辑下「过期条目重读」失败。

**实机验证**：改回 1920×1080 后，日志出现 `display topology changed; rescued windows count=1`，
停在 x=2500 的窗口被移回 x=1425，界面显示的两块屏分辨率也与系统一致。显示器已还原为
1920×1080。

### 整理会堆叠而不是排列（已修）

用探针实测了每个窗口报出的「最小尺寸」，结果很整齐：

| 窗口 | 当前尺寸 | 报出的最小尺寸 |
|---|---|---|
| Notepad / Terminal / Explorer / 计算器 / Orca | 各自当前尺寸 | **与当前尺寸完全相同** |
| clash-verge / magpie / msedge（已最小化） | 146×28 | 536×559 / 616×462 / 516×90 |

Windows 11 的现代化应用（XAML/组合层）对 `WM_GETMINMAXINFO` 的回答是「我现在就这么大」，而不是一条应用真正强制的下限。
布局据此认为「没有任何网格能满足所有窗口」，于是 `plan()` 直接进入 cascade：**8 个窗口沿对角线堆叠、互相遮挡**——
与「收拢到一块屏上都能看见」正好相反。实测日志 `applied=8 ... cascaded=true` 与探针的坐标都证实了这一点。

**修法**：最小尺寸是偏好而非禁令。改为只有当**规划下限**（fallback 320×200）都放不下时才 cascade；
否则交给 `grid()`——它本就会按「被压到最小尺寸以下的窗口数」排序并标记 `clamped_to_min`。

**实机验证**（同一桌面、8 个窗口）：整理后为 3×3 平铺
（列 x=12/646/1280，行 y=12/350/688，单元格 626×330），只有 Orca(408) 与计算器(540) 因自身最小尺寸略高于一行，
`refused=0`（都接受了）。修复前是 8 层对角堆叠。

新增两个布局测试：用上表的**真实测量值**做夹具，断言「最小尺寸等于当前尺寸时仍应平铺」；
以及「窗口数超过下限容量时仍应 cascade」（30/40 个窗口）。已验证还原判定会让前者失败。

`probe --mins` 是定位这个问题时加的诊断选项，保留——它打印的正是布局决策所依赖的数据。

### 三种排列方式中有两种完全相同（已按决定修正）

读代码发现 `网格` 与 `顺序` 走的是同一条路径：同一次排序（焦点优先、再按位置）、同一个 `grid()`
函数，只有返回的标签不同——也就是说「顺序」这个选项什么也没做。

按你的选择处理：**保留三项，让「顺序」真正不同**——它忽略焦点。

| 模式 | 行为 |
|---|---|
| 网格 | 等分单元格；有焦点的窗口放第一格 |
| 顺序 | 按原屏幕位置顺序；**不受焦点影响**（同一桌面每次整理结果一致） |
| 主次 | 焦点窗口占主区域（不变） |

实现上排序键依赖模式（`focus_first = !matches!(mode, PreserveOrder)`），新增两个测试
（`preserve_order_ignores_focus`、`grid_puts_the_focused_window_first`），并更新两种模式在界面上的说明文案。

**未做实机焦点验证**：焦点差异只在某个被整理窗口持有焦点时可见，而当前会话仍是锁屏状态（前台是锁屏界面），
无法让目标窗口获得焦点。语义由上述单元测试固定；几何（单元格划分）此前已在实机验证（3×3 平铺）。

### 目视审计发现的三处（本轮）

**1. 「上次整理未完成」在布局进行中就出现，且永远清不掉。**

`pending_work` 扫描账本目录并跳过「引擎自己拥有的那笔」，比较的是事务 ID。而账本文件名用一个
新 UUID、文件内部又由 `Journal::begin` 另生成一个——两者永远不同，于是这笔「自己的」账本每次都被
当成「别人留下的未完成工作」。界面上就是：整理刚成功，红色横幅却说上次没做完，点「尝试恢复」也没用。

修法：让调用方指定事务 ID，文件名与内部记录用同一个（`Journal::begin_named`）。实测：整理后文件名
`f3fbd19b….journal` 与日志中的 `transaction=f3fbd19b…` 一致，横幅消失。

**2. 窗口「移动失败」却被缩放了。**

clash-verge 这类窗口接受 `SetWindowPos` 的尺寸、但坚持自己的位置。引擎读出「位置不符」→ 判定失败 →
但尺寸已经改了，用户看到的是一个被缩小/放大的窗口。修法：判定为 Rejected/Unknown 时，把窗口尺寸
恢复成账本里的原尺寸（位置保持它实际所在处，不重试那个已经失败的位置）。新增假后端行为 `SizeOnly` 与
端到端测试；禁用该修复后测试立即失败（窗口被拉到 1896×1016，原本 600×500）。

**3. 显示器卡片的比例与实际分辨率不符。**

截图用 `object-cover` 填充一个固定高度的盒子，等于把 16:9 的画面裁成盒子的比例。修法：卡片改为
CSS grid，列/行由显示器的真实坐标区间决定，截图盒严格取显示器的宽高比。
过程中还发现：左右并排的两块屏因为 y 原点相差 78px（各自任务栏位置不同）被排成了对角——
改为按**区间重叠**判断同一行/列，而不是比较原点数值。实测两块 16:9 卡片并排、等高、比例正确。

另外：预览按钮原先只在「没有活动布局」分支里出现，布局一旦启用就找不到；现在它属于任何状态
（只读操作），并保持主色调可见。

### 设置页无法滚动（本轮目视审计发现，影响所有长页面）

设置页有 10 张卡片，默认窗口 679 逻辑像素高，**底部「重置 / 帮助 / 隐私」三张卡完全够不到**，
滚动条也不出现。原因是一个经典的 flex 缺陷：`<main className="flex-1 overflow-y-auto">` 的
`flex-1` 能让元素变高，但 flex 子项默认 `min-height: auto` 拒绝收缩到内容高度以下，于是
`overflow-y-auto` 永远不触发。

修法是给它加 `min-h-0`。验证方式：点击一个位于屏幕外的控件（「使用统计」开关），页面自动滚到它，
底部三张卡出现在视口内——修复前这个控件是够不到的。

**活动历史挤占概览**：18 条记录默认全部展开，占掉大半屏，把「布局预览」推到了视口之外。
改为默认显示 3 条 + 「显示全部 N 条」，实测「工具」卡片进入首屏。

**深色主题复核**：概览、设置两页在深色下配色一致，分隔线与边框可见，无低对比文本。

### 引导页与概览的信息层级（第二轮目视）

**引导页**：内容块原先用 `justify-center` 且限宽 512px，第一步只有三句话时整块悬在窗口中央，
上下各有大片空白，按钮离正文很远。改为：内容宽到 576px（`max-w-xl`）、标题放大到 `text-xl`、
正文与按钮间距加大，步骤指示器把当前步从 6px 圆点改成 16px 长条——6px 的实心点在四个空心点里
几乎看不出，用户无法判断还剩多少。同时「上一步」的禁用态从 `opacity-40` 提到 `55`，
在第一步时是一个可辨识但不可点的按钮，而不是一个看起来坏掉的控件。

**概览**：
- 「已收拢窗口 —」在空闲时是一行纯噪音，改为零值时不渲染。
- 「标记为远程会话」原先是详情行下方的一个文字链接，视觉上像脚注——但它是托盘被隐藏时
  唯一能告诉应用"会话开始了"的入口。移到操作行，成为与其他动作同级的按钮。

实测：概览三张卡在 718px 窗口内一屏可见；引导五步逐页截图确认。

### 排除页：控件归属（第三轮目视）

「清空规则」原在「正在运行」卡片的标题栏，读起来像"清空下面这个列表"——而下面列的是运行中的应用，
它并不动它们。移到「排除的应用」卡片，与规则计数并列；同时在没有规则时**隐藏**而不是置灰：
一个存在、样式像操作、点了没反应的控件，比没有控件更糟。

实测：空状态时该按钮不存在；添加 `notepad.exe` 后出现在规则计数旁，对应开关自动同步为开启；
点击后规则清空、设置文件回到 `excluded_apps: []`。

### 「部分受限」时点名拒绝恢复的应用（第三轮目视）

后端一直在计算 `pending_apps`（哪些应用的窗口没能恢复），但界面从未使用它——提示只说
「有窗口没能恢复到原位。可以再试一次，或先关闭这些窗口。」用户得自己在任务栏里找。

现在在提示下方列出应用名（等宽块），并给「排除这些应用」一个直接入口。目视确认：文字、
应用名块与链接在同一行，与下方按钮组不冲突。

同时把单显示器提示从详情行之间移到操作行正下方——整理按钮在只有一块屏时是禁用的，
解释它的句子原本夹在「布局」和「远程检测」两行之间，很容易被当成布局说明的一部分。

**流程教训**：中途我一度以为新界面没生效，实际是 `cargo build` 早于 `npm run build`——
Tauri 把前端嵌进二进制，必须在前端产物更新后重建后端。两次重建之间的时间戳是判断依据。

### 单显示器状态与最窄窗口（第三轮目视，实测）

用 `ChangeDisplaySettingsEx` 把第二块屏从桌面分离（标志位 0，**不写注册表**），复现单屏：

- 整理按钮正确置灰；
- 「当前只检测到一块显示器…」的说明紧贴在按钮下方，而不是原来夹在详情行之间；
- 目标显示器自动回退到「显示器 1（主）」。

恢复用 `DisplaySwitch /extend`（`ChangeDisplaySettingsEx` 重新挂载返回 -1，说明分离后该 API 的
重新挂载路径不可用）。恢复后两块屏回到原位（DISPLAY2 在 -1920,-78），应用自动撤销单屏提示。

**最窄窗口 720×520**：按钮行仍能横排，详情行不挤压，活动列表正常；侧栏固定 192px 在此宽度下
占比约 27%，属可接受范围。

### 深色主题下禁用按钮几乎不可见（本轮目视，实测对比度）

引导页第一步的「上一步」是禁用态。原来的处理是整元素 `opacity-55`，于是**填充与被压暗的文字一起褪色**：
在深色卡片上实测约 **2.9:1**，低于 4.5:1 的可读下限，看起来像"缺失"而不是"暂不可用"。

修法：不再整体降透明度，而是按变体分别处理——填充用 `accent-soft` 变暗，文字统一改用
`--color-muted`（深色下 0.63，估算 5.6:1，达标）。深色实测：文字清晰可读，按钮仍明显不可点。

**另有一处自查**：我一度想把深色 accent 从纯灰改成带色相（好让主按钮更像"主操作"），
但 `design.test.ts` 里明确写着 **near-neutral、且蓝色强调色曾被明确否决**。这是产品决策不是疏漏，
所以撤回改动，只在注释里记下"为什么保持中性"。浅色与深色下的主/次按钮对比度实测分别正常。

### 「没有接受位置调整」的文案只说对了一半（本轮实测）

解锁会话后做了一次真实整理，`refused=1`：被拒的是 `python.exe`，探针显示它的**最小尺寸 698×846
大于目标格子**——原因是"太大，放不进"，而不是"会自己纠正位置"。而卡片文案当时写的是
「这些应用会自己纠正窗口位置」，对终端、IDE 这类窗口是错的。

改为覆盖两种真实原因：「有的会自己纠正，有的大到放不进格子」。实测截图确认。

顺带确认：`last_refused_apps` → 卡片 → 「排除」这条链路在真实拒绝下从头到尾可用。

**焦点语义仍未能实机验证**：系统拒绝把前台交给其他应用（`SetForegroundWindow`、`AppActivate`、
Orca 点击三种方式都试过，前台始终回到宿主进程），因此无法让被整理的窗口持有焦点。该语义由
`grid_puts_the_focused_window_first` 与 `preserve_order_ignores_focus` 两个单元测试固定，
且从 `GetForegroundWindow` 到布局的链路已在代码层核对完整。

### 两块同分辨率显示器被画成不同宽度（本轮目视）

引导第 2 步的两块屏都是 1920×1080，卡片却明显不等宽——左窄右宽。原因不在区间计算
（两列都是 1920），而在 CSS：裸 `Nfr` 等价于 `minmax(auto, Nfr)`，其自动最小值是该列的
min-content 宽度。右侧卡片多一个「使用中」标签，min-content 更大，于是从邻列偷走了宽度。

改为 `minmax(0, Nfr)`。实测：两卡各约 283px，等宽、比例一致。

### 延迟恢复：提示指向不存在的按钮，之后永久停在「正在恢复布局…」（本轮实测，三处）

这一轮把「等待恢复」这个状态真的跑了一遍（把 `restore_delay_secs` 调大，解除远程标记触发自动恢复），
发现三处问题，都在同一条链上。

**一、倒计时指向的按钮不存在。** 文案是「{n} 秒后恢复布局。现在点「整理到目标屏」可以取消。」，
但等待期界面里没有这个按钮——它是「保留当前布局」。用户照着提示去点，找不到。

**二、「保留当前布局」并不能取消等待。** 它只清事务和 preimages，没有动 `Schedule` 的令牌，
所以即使点中，计时器到点仍会恢复。`Schedule::cancel()` 早就存在，只是没有接上去。

**三、恢复结束时界面不落地。** `restore_blocking` 与 `monitor::restore` 都不发 `phase: "done"`
（只有 `migrate` 发）。前端用这组事件维护 `busy`，于是倒计时走完后：提示永久停在
「正在恢复布局…」不消失，`busy` 仍是 waiting 分支设的 false，整排按钮看起来可点——而窗口正在移动。

三处一起修：文案改指「保留当前布局」（中英都改），`keep_current_layout` 调用 `schedule.cancel()`，
两条恢复路径都补发 `done`。

实测：25 秒延迟，解除标记 → 倒计时逐秒递减 → 恢复执行 → **横幅消失、状态回到「就绪」、按钮回到
「整理到目标屏」**。修复前同一时刻是永久停住的。

### 轮换目标屏的进度流不闭合（本轮）

`cycle_target` 只发 `phase: "migrating"`，从不发 `done`——gather 和 restore 两条路径都会收尾，
只有它不会。按钮本身经 `run()` 的 `finally` 复位，所以用户看不到症状；但事件流上这是一批
"开始了永不结束"的迁移，任何新的观察者都会因此误判。

补发 `done`。实测轮换后界面稳定、无卡顿，目标正确切到下一块屏。

### 缩略图全黑：一次自我纠错

中途我怀疑缩略图与显示器错位（探针显示 DISPLAY1 有内容而卡片是黑的），并怀疑 BitBlt 在
锁屏下失效。复核后两条都是我的探针出错：显示器 2 在左侧（`-1920, -78`），我第一次按
`(1920, 0)` 抓的是空白区域。

`OpenInputDesktop` 与 WTS 都会报告 "Active"，但 BitBlt 仍可能返回全黑——那是屏幕物理关闭
（显示器超时休眠）时的正常现象，不是缺陷。「没有画面」在这种情况下是诚实的描述，没有改动。

### 工具会移动它自己的窗口（本轮实测，已修）

`SkipReason::OwnWindow` 在枚举里存在、有 `code()`、也参与 "这是一次跳过吗" 的判断，但**从来没有
任何地方产生它**：`classify` 里根本没有这一分支，`EngineConfig` 也不知道自己的进程是谁。

后果在实机上是可见的：`probe --mins` 列出的可整理窗口里有一行 `conflux.exe 511,161 898x711`。
一次整理会把工具自己塞进网格、推到另一块屏，而用户正在它上面点按钮。

修法：`EngineConfig` 增加 `own_process_id`，`classify` 最先检查它并返回 `OwnWindow`（先于排除规则，
也先于 `is_migratable`，否则一个刚好最小化的自身窗口会被报成 `Invisible`，掩盖真实原因）。匹配
pid 而不是 `"conflux.exe"`，这样第二份安装或并排的调试版仍然是普通窗口。

实机验证：整理 12 个窗口后，`conflux.exe` 仍在 `511,161 898x711`，一字不差；预览里的候选列表
为 11 个，工具自己不在其中。新增 `the_engine_never_moves_its_own_windows`，并确认把守卫去掉它
会失败。

### 预览里两个标签叠印（本轮目视，已修）

布局预览中 clamped 窗口（比格子大）会盖住相邻单元格，两个应用名正好落在同一处在像素上叠印，
「Notepad #5 / python」读成一片。先把 clamped 的标签贴到底边（重叠从左上角向右下增长），
`python` 那处解决了，但 `Orca / Notepad #4` 仍叠——两个都是居中标签，只差一行字。

最终按通用手段处理：给所有标签加 `stroke` 光晕（`paintOrder="stroke"`，颜色取卡片底色）。
实测两处都能读清。几何上仍紧贴，但强行拉开会让标签跑出自己的矩形，得不偿失。

### 撤回上一轮的 `own_process_id`（判断错误）

上一轮我声称"工具会移动自己的窗口"，并据此加了 `EngineConfig::own_process_id`。**这个判断是错的。**

证据：`crates/platform/win/src/windows_impl.rs` 的 `enumerate()` 里一直有
`if raw.snapshot.id.process_id == self.own_process { continue; }`，而 `WinPlatform::enumerate`
正是应用自己走的那条路（`WinPlatform::new()` 在应用进程内构造）。应用从来不会移动自己的窗口。

我犯的错是**用 `probe`（独立进程）的枚举结果当作应用行为的证据**：probe 的 `own_process` 是 probe
自己的 pid，所以它列出 `conflux.exe` 是正确的，这不能说明应用会移动自己的窗口。

已撤回 `own_process_id`、对应测试与文案。标签光晕那部分（同样是那一轮提交的）是有效的，予以保留。

### 六个从未被构造的跳过原因（本轮审计，已删）

按"定义了但从未产生"这条线索系统扫了一遍 `SkipReason`：`OwnWindow`、`ZeroSize`、`ToolWindow`、
`ShellWindow`、`ModalChild`、`OtherVirtualDesktop` 在业务代码里**没有任何构造点**，只出现在
`code()` 的匹配和 `skip_codes_are_unique` 的清单里。

它们的过滤发生在平台层（隐藏窗口、工具窗口、cloaked 窗口、自身进程），引擎根本拿不到这类窗口。
于是这六个变体连同 `api.ts` 里的六条中文标签，都是用户永远看不到的死代码。

`Invisible` **保留**：它在 `classify` 里是活的（显示器找不到时的兜底），审计时一度想把它一起合并，
跑构建前复核发现它是可达的，已恢复。

删除后：Rust 全套通过、clippy 干净、前端 96 测试通过，实机预览正常（标签光晕仍在生效）。

### 一次"设置页不能滚动"的误判，以及换来的可靠工具（本轮）

我一度判定设置页无法滚动，并据此给外层 flex 容器加了 `min-h-0`。**这个结论是错的。**

起因是滚轮、PageDown、Tab 三种方式都没让页面移动。我给应用挂上
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`，用 CDP 直接读 DOM：

```
设置页 main: scrollHeight=2167 clientHeight=631 canScroll=true
程序化设置 scrollTop=1500 -> 生效，最大 1536
```

滚动容器一直是好的。真正的问题是我的输入注入到不了 WebView2（Orca 的 `key`/`scroll` 与
`SendInput` 都无效），所以那三次"失败"证明的是工具的限制，不是产品缺陷。`min-h-0` 已撤回。

这次误判换来一个可靠手段：CDP 可以问出截图看不出的东西。用它把四个页面在

|---|---|---|---|---|
| 概览 | 不滚 | 可滚 | 无 | 无 |
| 显示器 | 可滚 | 可滚 | 无 | 无 |
| 排除的应用 | 不滚 | 可滚 | 无 | 无 |

截断检测同时看 `text-overflow: ellipsis` 的实际溢出与 `overflow:hidden` 的元素，均无命中；

### 又一次自我纠正：两处"不对齐"都不是缺陷

英文设置页底部文字看起来被裁，实际是页面未滚到底——内容完整。

### 可视审计脚本（本轮，已接入 CI）

前几轮的对比度、截断、溢出检查都是我在会话里手工跑 CDP 做的，跑完就没了。这轮把它固化成
`scripts/ui-audit.mjs`，并加进 CI 的 `ui-audit` job。

覆盖 4 个页面 × 2 套主题 × 2 种窗口尺寸 = **16 个组合**，每个组合检查：文字对比度、
`overflow:hidden`/`text-overflow:ellipsis` 造成的截断、文档水平溢出、按钮越出视口、
`<main>` 滚动容器是否存在。任一命中即以退出码 1 失败。

**这个脚本在写成的过程中先后错了三次，每次都是"看起来通过"：**

1. **固定 sleep 太短** → 报「主题按钮不存在」。改成等标题出现再操作。
2. **解析不了颜色** → WebView2 把 `oklch()` 计算成 `lab(...)`，而我的解析器只认
   `rgba()`，于是每个颜色都是 `null`，**对比度检查从未真正执行**，脚本永远通过。
   改成用 canvas 让浏览器自己把颜色转成 sRGB。
3. **忽略半透明层** → 「没有画面」是白字压在 62% 不透明的遮罩上，我只找第一个不透明祖先，
   把它算成 1.11:1 的假阳性。改成自下而上合成所有层。

### 救援会搬动用户已排除的应用（本轮，已修并实测）

`rescue_offscreen` 只检查 `is_migratable()`，没有调用 `is_excluded()`。而「排除的应用」页承诺的是

排除规则没有「越界时例外」这一条：用户排除一个应用是为了让它完全不受干预，而救援恰恰是用户在

修法：救援循环里跳过被排除的窗口。新增 `rescue_leaves_excluded_applications_alone`，并确认
去掉守卫后它失败（`only the unexcluded window may be rescued`）。

### 排除规则的语义边界（本轮，补测试与文档）

| 路径 | 受排除约束 | 理由 |
|---|---|---|
| 整理（`classify`） | 是 | 主动移动 |
| 救援 | 是（上一轮补） | 主动移动 |
| 恢复 | **否** | 把窗口放回原位，与"移动"相反 |
| 恢复时的尺寸修正 | **否** | 同上 |
| 显示器消失后的兜底 | **否** | 不这么做窗口就丢了 |

### 数值输入越界后显示与实际不符（本轮，已修并实测）

边距与间距是 0–200 的数字输入。输入 `999` 后失焦：

| 位置 | 值 |
|---|---|
| 输入框显示 | **999** |
| 设置文件 | **200** |

输入是非受控的（`defaultValue`），提交时钳制到 200，但输入框保留用户键入的 999。页面不重载
就一直这样，用户看着 999 而实际生效的是 200。

修法：失焦时把钳制后的值写回输入框；无法解析时（空、非数字）回填当前值而不是留空。

实测：`999` → 显示 **200**，保存 200；空 → 显示 **0**。

**一次测量失误**：我另一次尝试用 `dispatchEvent(new Event('blur'))` 触发，React 的合成事件没有
响应，于是显示"没保存"。那不是缺陷，是我的测试手法不对——`focus()` + `blur()` 才走真实路径。

### 同一缺陷的第二个实例：恢复延迟（本轮）

是因为这已经是第二份副本——规则只存在于两个 `onBlur` 里时，第三个数字输入很容易写出自己的版本。

`commitNumber` 的一个决定：**空输入恢复当前值，而不是 0**。`Number("")` 是 0，直接用它会把
15 秒的延迟悄悄改成 0，是用户没要求的真实变更。

实测：

| 输入 | 失焦后显示 | 保存 |
|---|---|---|
| margin `999` | 200 | 200 |
| gap 空 | 8（原值） | 8 |

### 跨年的活动记录无法区分（本轮，已修并实测）

### 恢复 journal 失败时引擎仍显示「就绪」（本轮，已修，未测）

`recover()` 在 `JournalCorrupt` 时直接 `?` 返回，**没有设置 `self.state = Error`**。引擎保持初始的
`Idle`，界面显示「就绪」——而一份读不出来的 journal 意味着可能有窗口停在错误位置。

两处都改为先设 `Error` 再返回。

**这个分支的测试构造不出来，原因值得记录**：`conflux_journal::recover` 把任何解码失败都当作
「尾部截断」（`truncated`），因为那是写入被打断的正常形态，随后返回 `Clean` 或 `Unfinished`。
所以损坏的**内容**永远不会走到 `Err`。`JournalCorrupt` 只在文件打不开时出现——被删除、被锁、
权限不足，那是 IO 状态而不是字节模式，无法用一段固定内容复现。

我先后写了两个测试试图覆盖它：第一个用乱码，失败（`recover` 返回 Ok）；第二个用"先写后删"，
通过了但断言的是"缺失文件返回 Idle"，与被测函数名和意图相反，**没有价值**，已删除。最终选择不
伪造测试，而是在代码注释里写清为什么这里没有测试。

### 七处裸按钮用 opacity 表达禁用态（本轮，已修并量化）

`Button` 组件在几轮前就改成了「变填充+变文字色」，但七个**裸 `<button>`** 仍是 `disabled:opacity-*`。

用真实令牌值算（不是估算）：`--color-muted` 在卡片上 **5.03:1**，达标；但降低透明度立刻跌破门槛：

| opacity | 对比度 | |
|---|---|---|
| 1.00 | 5.03:1 | OK |
| 0.90 | 4.34:1 | FAIL |
| 0.55 | **2.43:1** | FAIL |
| 0.40 | **2.62:1**（实心按钮） | FAIL |

关键结论：**muted 文字只要降低任何透明度就不达标**，所以不能靠调 opacity 的数值解决。

修法分两类：
- 三处文字链接（排除这些应用 / 删除规则 / 清除快捷键）→ 直接去掉 opacity。它们禁用只为防重复点击，`busy` 实测约 11 ms。
- 两处实心按钮（请求授权 / 尝试恢复）→ 改用 `disabled:bg-accent-soft` + `disabled:text-muted`，与 `Button` 一致。
- 两处（快捷键输入框 / 引导的检测选项）→ 改用 `disabled:text-muted`。

`ui-audit.mjs` 增加了禁用态对比度检查（按有效颜色合成，不是只看令牌）。但实测发现它在**默认审计状态下抓不到问题**：那时没有禁用控件（`busy` 为 false、排除列表为空），按钮根本不存在。这个限制如实记下，不假装已覆盖。

### 审计脚本的禁用态检查：一次误判与一次真实局限

上一轮我写"默认状态下没有禁用控件"，**这是错的**。逐页统计后：排除页有「添加」（输入为空）、

### `Segmented` 的禁用态完全无反馈（本轮，已修）

设置页有四组 `Segmented`（界面语言、主题、远程端能看到、检测灵敏度），都传了
`disabled={busy}`，但组件内没有任何 `disabled:` 样式——`busy` 时点击无效，外观一模一样。

修法：**只让选中项**从 `fg` 降到 `muted`。

为什么不是整组淡化：muted 文字在该背景上是 5.44:1，60% 透明度降到 **2.71:1**，低于门槛；
而 `--color-border` 已经是调色板里最淡的边框令牌，没有"更淡但仍合法"的状态可选。

结果是禁用时读起来像"当前选择失效"，而不是"整组不可用"。`disabled` 仍然挡点击，`busy` 约 11 ms，
比一个读不清的标签问题更小。这个取舍写进了组件注释。

**未能运行时验证**：`busy` 只有约 11 ms，抓不到；强制设 `button.disabled = true` 不会触发 React
重算 className，所以那种测法无效（我试过，得到的是假阳性）。改动本身是 `disabled ? muted : fg`
的纯条件，已由类型检查与代码审阅确认。

改成三次运行：**中文浅色、中文深色、英文浅色**（24 组合）。英文只跑一次，因为长度溢出与配色无关。

过程中脚本自己出了四个问题，都修了：

1. **语言顺序**：先找页面再切语言，而第一次运行是中文，找 "Settings" 必然失败。
2. **切换后没等重渲染**：语言一换所有标签都变，下一步要找的按钮还没出现。
3. **污染下次运行**：语言和主题是持久设置，跑完停在 `en`/`light`，下一次启动状态不符预期，
   报错却指向页面（"settings page did not open"）。
4. **还原不完整**：只还原了主题，"跟随系统"在语言组和主题组各有一个，只点了第一个。

现在脚本结束时把语言和主题都还原为 `跟随系统`，连跑两次都干净。

**这几轮我反复把脚本自身的缺陷当成产品缺陷**——第 3 条尤其典型：报错说页面打不开，实际是上一次
运行留下的状态。

### 托盘菜单的启用规则（本轮，已提取并测试）

「未验证」清单里托盘一项原本写的是"需要人工点击或加测试入口"。其中**启用规则**这一半不需要外部
条件：它是纯数据推导，被埋在 `build_menu` 里，与 `AppHandle` 耦合所以测不了。

抽成 `menu_enabled(paused, has_layout, display_count) -> MenuEnabled`，`build_menu` 改为调用它。
三条规则现在有测试：

| 规则 | 断言 |
|---|---|
| 无布局时「恢复」「暂停」禁用 | `!idle.restore && !idle.pause` |
| 暂停时「整理」禁用但「恢复」保持可用 | `!paused.gather && paused.restore` |
| 「切换显示器」需要两块屏以上 | 0/1 禁用，2 启用 |

把 `gather: !paused` 改成 `gather: true` 后测试失败（`assertion failed: !paused.gather`）。

仍未验证的是**点击链路**：托盘图标不被无障碍接口识别，无法自动点击；`handle_menu_event` 的
`AppHandle` 在单元测试里构造不出来（`tauri` 未启用 `test` feature）。

### 预览图在 57 个窗口时糊成一片（本轮，已修并实测）

造出 57 个可整理窗口后，预览图是一团灰噪：所有 `Notepad #1..#57` 堆在左上角互相压印。

根因是字号的计算基准错了——`fontSize = max(work.width * 0.028, 10)`，1920 宽下恒为 **54 px**，
与格子多大无关。57 个格子只有几百像素时，54 px 的标签必然重叠。之前加的描边光晕只能分开**两个**
相撞的标签，分不开几十个。

改为按格子尺寸算字号（`min(w,h) * 0.22`），并在格子小于 96 px 时**不画标签**，让矩形自己说话；
`<title>` 仍然保留悬停时的完整名称。

实测同一组 57 个窗口：小格子的标签消失，只有少数较大格子（`Notepad #1`、`#11`、`python`）还有标签，
图形恢复可读。

### 顺带确认：那次的级联布局是正确的

预览数据 `clamped: 57`、每个窗口偏移 28 px、尺寸都是 332×202——这是**级联**，不是网格。
Notepad 的最小尺寸 332×202，57 个确实放不进 1920×1032，降级是设计行为，界面也有
「空间不足，窗口将叠放」的提示。**不是缺陷。**
